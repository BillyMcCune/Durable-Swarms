Durable Swarms

Recovering distributed workflow simulations

Pete Crowley · Billy McCune · Jonathan Ouwerx

The Problem: Keep Work Moving

  1. Multiple independent workloads share a fixed VM pool.
  2. Workers or daemons can fail or stop making progress.
  3. Replacement workers resume from durable state.
  4. The implementation simulates workflows; it does not yet run coding agents.

Workload Model

  1. Each workload declares one leader and child workers with dependencies.
  2. Steps simulate compute delays or workload-local counter effects.
  3. The leader yields its slot while waiting and collects child results.
  4. Seeded durations and fault schedules make simulated inputs reproducible.

Scheduling and Membership

  1. Configured VMs provide a fixed number of worker slots.
  2. The scheduler allocates at most one ready worker per workload per pass.
  3. Dependencies must complete before a child is ready.
  4. Replacement placement prefers another live VM, then the least occupied VM.

Detect, Fence, and Replace

  1. Lease expiry or a progress timeout identifies failed or stalled work.
  2. A new attempt ID fences stale worker requests.
  3. The leader authorizes failed child recovery; failed leaders are queued directly.
  4. The replacement resumes at the next incomplete step.

SQLite Is the Recovery Boundary

  1. Ordered events preserve workload and worker history.
  2. Checkpoint events capture workload state and next-step cursors.
  3. The current projection is rebuilt from checkpoint events after restart.
  4. SQLite uses WAL and synchronous=FULL on persistent storage.

Failure Injection and Tests

  1. Modeled faults include worker exit, VM daemon loss, stalls, retry loops, invalid results, and effect interruption.
  2. Tests cover leases, stale attempts, dependencies, recovery, durable effects, and orchestrator restart.
  3. Integration tests use local processes, not measurements on separate physical VMs.

Demonstration: Crash After an Effect

  1. Start the orchestrator and two VM daemons; submit the example workflow.
  2. The implementation worker exits after the simulated patch and before checkpointing.
  3. A replacement resumes, reuses the effect receipt, and completes.
  4. Inspect the event log and verify patches_applied = 1.

Boundaries and Next Steps

  1. One orchestrator and its durable database are the recovery boundary.
  2. The unauthenticated API is intended for a trusted network; isolation is logical.
  3. Real coding agents, external tool adapters, and cloud provisioning are future work.
  4. Measure recovery and overhead across actual machines.
